# AIDLC Vibe Coding 分段提示词

本提示词适用于 Amazon Q、Kiro、Codex 等可读写项目文件并执行命令的编码助手。按编号逐段输入，每次只输入一个代码块；助手完成并停止后，再输入下一段。

## 使用规则

1. 在目标项目根目录开启编码助手。
2. 从“第 0 段”开始，按顺序执行。
3. 遇到 `[Question]` 时，在聊天中回答，然后输入对应的“继续段”。
4. 不要跳过需求、设计和任务审阅门禁。
5. 新会话或上下文中断时，直接使用“恢复提示词”。
6. 第四、第五步默认每次只实现一个任务或测试一组用例，便于控制上下文和检查结果。

---

## 第 0 段：初始化与全局约定

```text
你现在负责使用 AIDLC 五步法交付当前软件项目。请直接操作当前项目文件，不要只给出建议。

全局规则：
1. 使用中文回复并编写 AIDLC 文档；代码标识符遵循项目现有规范。
2. 将 .aidlc 作为项目事实来源和中断恢复日志。
3. 保留已有代码、文档和用户改动，不覆盖或回退不属于本次任务的修改。
4. 每次开始前读取当前阶段的计划文件和已有产物，从最后一个未完成项继续。
5. 所有计划、问题、回答、关键决策、验证命令和结果都写入对应文档。
6. 只有满足当前阶段门禁后才能进入下一阶段。
7. 遇到会改变业务范围、验收、安全或架构的未知信息时，使用 [Question] 和空白 [Answer] 记录并停止，不要自行决定。
8. 优先采用简单、成熟、与现有项目一致的方案，避免过度设计。

请执行：
- 检查当前目录、版本控制状态和已有文件。
- 幂等创建以下目录，不覆盖已有内容：
  - .aidlc/plan
  - .aidlc/requirements
  - .aidlc/design
  - src
- 判断当前 AIDLC 阶段。
- 只汇报当前阶段、已有产物、缺失产物和下一段应该执行什么，不要提前生成阶段产物。
```

# 第一步：需求分析

## 第 1A 段：分析需求并提出关键问题

把项目的初始需求附在本段末尾再执行。

```text
你是一位专业产品经理。请把模糊需求转化为清晰、可验证、可供设计阶段使用的需求基线。

执行前：
1. 读取 .aidlc/plan/req-plan.md（如果存在）。
2. 读取 .aidlc/requirements 下已有的全部文件（如果存在）。
3. 阅读当前项目说明、现有代码概况和下面的初始需求。

创建或续写 .aidlc/plan/req-plan.md，至少包含：
- 上下文和当前状态
- 带复选框的需求分析计划
- 问答记录
- 决策与变更记录

检查以下信息是否明确：
- 产品目标、目标用户、角色和权限
- 核心业务对象及生命周期
- 正常、异常和批量操作流程
- 数据输入、输出、导入导出和保留
- 外部系统、认证、通知和失败处理
- AI/Agent 的权限、人工确认、降级和可追溯性
- 部署方式、技术限制、性能、安全和合规
- MVP 范围、不做事项和验收标准

如果存在会影响范围或验收的缺口：
- 在 req-plan.md 中集中生成 3 至 7 个关键问题。
- 使用以下格式并保持 [Answer] 为空：

### Q-001
[Question]
问题正文

[Answer]

- 向我列出这些问题后停止，不要生成最终需求文档，不要自行补答。

如果问题已经全部回答，则继续完成需求文档，不要重复提问。

初始需求：
【在这里粘贴项目需求】
```

```text
- .aidlc/requirements/non-functional-requirements.md

- FR-xxx：功能需求

最后：
- 汇总完整需求清单。
- 检查所有编号和文档之间的一致性。
- 更新 req-plan.md 的复选框和完成状态。
- 汇报生成文件、需求数量、待确认事项以及是否满足进入设计阶段的门禁。

我的答案：
【按 Q-001、Q-002 的编号粘贴答案】
```

```text
- 修订后重新执行需求完整性和一致性检查。

【粘贴新增或修改的需求】
```

# 第二步：设计文档

## 第 2A 段：设计分析与技术问题

```text
你是一位资深软件架构师。请基于已确认的需求设计系统，不编写具体业务代码。

执行前：
1. 完整读取 .aidlc/requirements 下全部文件。
2. 读取 .aidlc/plan/design-plan.md 和 .aidlc/design 下已有文件（如果存在）。
3. 检查现有项目、技术配置和代码边界。

创建或续写 .aidlc/plan/design-plan.md，包含：
- 输入需求基线
- 带复选框的设计步骤
- [Question]/[Answer] 问答记录
- ADR 技术决策记录

设计原则：
- 按高内聚、低耦合划分领域和模块。
- 明确组件职责、依赖方向和跨领域接口。
- 采用满足需求的最直接方案，避免无依据的微服务或复杂平台化设计。
- 可以使用 Mermaid、表结构和 JSON 示例，但不要编写控制器、组件或数据访问实现代码。
- 设计鉴权、权限、事务、并发、幂等、错误、审计、重试和降级。
- AI/Agent 设计必须包含工具边界、权限继承、人工确认、上下文、可观测性、超时重试和降级路径。

如果存在无法从需求或项目上下文确定、且会显著影响成本、安全或可逆性的技术问题：
- 在 design-plan.md 使用 DQ-xxx、[Question] 和空白 [Answer] 记录。
- 向我列出问题及各选项的影响后停止。
- 不要擅自完成关键技术决策。

如果没有未回答的关键问题，则直接完成设计阶段。
```

## 第 2B 段：写回技术答案并完成设计

```text
继续设计阶段。

重新读取 design-plan.md、全部需求文档和已有设计草稿。把本次消息中的答案准确写入对应 [Answer]。

如果仍有空白 [Answer]，列出问题并停止。

答案齐全后，生成或完善：
- .aidlc/design/system-architecture.md
- .aidlc/design/database-design.md
- .aidlc/design/api-specification.md
- .aidlc/design/frontend-design.md
- .aidlc/design/technology-stack.md
- .aidlc/design/traceability-matrix.md

要求：
- 系统架构覆盖领域、组件、部署、安全边界、外部集成和故障降级。
- 数据设计覆盖实体、字段、约束、索引、关系、审计、迁移和统一统计口径。
- API 设计覆盖路径、方法、权限、请求、响应、错误、幂等、分页和 Webhook 安全。
- 前端设计覆盖路由、信息架构、组件职责、状态管理、权限、加载/空/错误状态和响应式行为。
- 技术栈记录选择、理由、约束和替代方案；不要虚构未确认的版本。
- 追踪矩阵把每项 FR 和关键 NFR 映射到设计章节、数据实体、API、页面和验证方式。

完成后：
- 检查术语、状态、权限、数据模型、API 和前端是否一致。
- 更新 design-plan.md 的复选框和决策记录。
- 汇报设计文件、主要技术决策、残余风险以及是否满足进入任务规划阶段的门禁。

我的技术答案：
【按 DQ-001、DQ-002 的编号粘贴答案】
```

# 第三步：实现任务规划

## 第 3A 段：生成任务列表

```text
你是一位专业的软件开发管理人员。请把已确认的需求和设计拆成按依赖顺序执行的开发任务。

执行前完整读取：
- .aidlc/requirements 下全部文件
- .aidlc/design 下全部文件
- .aidlc/tasks.md（如果存在）
- 项目配置、现有 src 结构和测试结构

生成或修订 .aidlc/tasks.md。

每个任务必须包含：
- 唯一编号 T-xxx
- 默认未勾选的复选框
- 目标
- 范围与不包含内容
- Depends on
- 精确到当前行号的需求引用
- 精确到当前行号的设计引用
- 必要时使用 [Reference] 标记非常见外部库的 API 文档
- 实现要点
- 可观察、可测试的验收标准
- 具体验证命令或验证方式
- 交付物

任务规则：
- 按真实前后依赖排序，禁止循环依赖。
- 每项任务应产生独立价值，粒度适中。
- 不要按每个文件或函数机械拆分。
- 覆盖全部需求和设计范围，包括配置、迁移、测试、集成失败处理和必要文档。
- 引用格式使用“相对路径:行号”，确保可在命令行访问。

在文件顶部写入：
- 审阅状态：待审阅
- 范围基线
- 最近审阅记录

生成后停止，不要开始写代码。向我汇报任务数量、主依赖链、主要里程碑和仍需补充的 [Reference]。
```

## 第 3B 段：根据评审意见修订任务

```text
请根据下面的评审意见修订 .aidlc/tasks.md。

规则：
- 先重新读取全部需求、设计和当前 tasks.md。
- 保留合理的已有任务编号；新增任务使用新编号。
- 同步更新依赖、排序、引用、验收标准和验证方式。
- 检查所有需求是否至少被一个任务覆盖。
- 审阅状态仍保持“待审阅”。
- 完成后停止，不要实现代码。

评审意见：
【粘贴评审意见】
```

## 第 3C 段：认可任务并进入开发

```text
我认可当前 .aidlc/tasks.md。

请执行：
- 重新读取 tasks.md，确认没有空白的关键 [Reference]、循环依赖或不可验收任务。
- 将审阅状态更新为“已认可”。
- 记录认可日期、认可来源和当前需求/设计基线。
- 只汇报第一个未完成任务的编号、目标、依赖、引用和验证方式。
- 不要在本段实现代码。
```

# 第四步：逐任务实现

## 第 4A 段：实现下一个任务

每完成一个任务后，重复输入本段。

```text
你是一位资深软件开发工程师。请只实现 .aidlc/tasks.md 中第一个未勾选的任务，不要同时实现后续任务。

执行流程：
1. 读取 tasks.md 的审阅状态；未认可则停止。
2. 读取该任务全文、依赖任务和所有需求、设计、[Reference] 引用。
3. 检查依赖任务是否完成。
4. 阅读任务影响范围内的现有代码、测试、配置和未提交改动。
5. 使用与项目一致的架构和编码风格完成最小必要实现。
6. 添加与风险相匹配的测试。
7. 运行任务规定的验证命令，并检查实际输出。
8. 失败时定位根因并修复，直到验收标准满足。

只有同时满足以下条件才可勾选任务：
- 交付物真实存在并可运行。
- 每项验收标准都有验证证据。
- 构建、类型检查、静态检查和相关测试通过。
- 未通过硬编码假数据、吞异常、跳过权限或禁用测试伪造完成。
- 接口、配置、迁移和相关文档保持一致。

完成后：
- 在任务下记录实现摘要、修改文件、验证命令和结果。
- 勾选且只勾选本次完成的任务。
- 汇报本次改动、验证结果和下一个任务。
- 然后停止，等待我再次要求继续。

如果任务无法完成：
- 保持复选框未勾选。
- 记录已完成部分、真实阻塞和解除阻塞所需信息。
- 停止，不要绕过问题实现后续任务。
```

## 第 4B 段：修复当前任务

当前任务验证失败或评审不通过时使用。

```text
当前任务尚未通过，请继续修复，不要开始下一个任务。

先读取：
- 当前未完成任务及其验收标准
- 相关需求和设计引用
- 已有实现、测试、运行日志和下面的反馈

要求：
- 稳定复现问题并定位根因。
- 从整体设计和数据不变量出发修复，不做只覆盖单个输入的临时补丁。
- 添加或修订防回归测试。
- 重新运行该任务的全部验证。
- 只有全部验收通过后才勾选任务并记录证据。

问题或评审反馈：
【粘贴错误日志、失败现象或评审意见】
```

## 第 4C 段：实现阶段完成检查

```text
请检查实现阶段是否可以结束。

执行：
- 读取 .aidlc/tasks.md，确认全部任务已勾选且有验证记录。
- 检查需求到任务的覆盖关系。
- 运行项目级构建、类型检查、静态检查和现有自动化测试。
- 检查启动说明、配置示例、数据库迁移和外部集成配置是否与实现一致。
- 不要在发现失败时宣告完成；定位并修复属于已实现范围的问题。

最后汇报：
- 完成任务数量
- 项目级验证命令和结果
- 未解决风险或环境限制
- 是否满足进入全面测试阶段的门禁
```

# 第五步：测试与 Bug 修复

## 第 5A 段：建立测试计划

```text
你同时扮演测试工程师和开发工程师。请基于需求建立真实可执行的测试计划，不要只做理论分析。

执行前：
- 完整读取 .aidlc/requirements 下全部文件。
- 读取 .aidlc/tasks.md、设计中的验证约束和现有测试。
- 读取 .aidlc/plan/test-plan.md（如果存在），从最后未完成项继续。

创建或完善 .aidlc/plan/test-plan.md，包含：
- 测试环境、版本、依赖和测试数据
- 带复选框的测试用例
- 每项用例的需求引用、前置条件、步骤、预期、实际、证据和缺陷
- 缺陷记录
- 回归测试
- 最终测试结论

优先覆盖：
- 核心角色端到端主流程
- 权限拒绝和数据隔离
- 状态流转、工作量、完成百分比和进度统计
- 批量操作、依赖、里程碑和健康度
- 外部通知、命令回调、重试和降级
- AI/Agent 工具权限、人工确认、结构化输出和降级
- 数据导出
- 关键性能、安全、兼容性和恢复要求

本段只建立或补全测试计划，不执行测试。完成后汇报用例数量、覆盖范围、测试环境依赖和第一组待执行用例。
```

## 第 5B 段：执行下一组测试并修复

每完成一组后重复输入本段。

```text
请执行 test-plan.md 中下一组未完成且相关的测试用例。

要求：
1. 启动真实应用及可用依赖，记录环境和启动日志。
2. 实际执行自动化测试、API 请求、数据库检查或必要 UI 操作。
3. 使用命令输出、响应、日志、持久化结果、截图或测试报告作为证据。
4. 通过后填写实际结果和证据并勾选。
5. 失败时先记录 BUG-xxx、复现步骤、严重级别和证据。
6. 定位根因并直接修复代码。
7. 添加防回归测试，重跑原失败用例和受影响的相邻路径。
8. 修复和验证完成前不要勾选失败用例。

因凭证、网络或平台环境无法执行时：
- 标记为“阻塞/未执行”。
- 记录原因、影响和解除阻塞条件。
- 不得把理论判断记为通过。

本次只处理一组相关用例。完成后更新 test-plan.md，并汇报通过、失败、修复、阻塞和下一组测试。
```

## 第 5C 段：全面回归与最终验收

```text
请执行最终回归和验收。

执行前：
- 读取完整 test-plan.md、全部需求和本阶段所有代码修复。
- 只要测试阶段修改过代码，就必须执行受影响模块、相邻接口和核心主流程回归。

执行：
- 完成所有剩余测试和回归测试。
- 重新运行项目级构建、静态检查、类型检查和自动化测试。
- 在真实运行环境验证应用可以启动并完成核心用户流程。
- 将每项结果和证据写入 test-plan.md。
- 检查所有阻断和严重缺陷均已关闭。
- 对无法执行或保留的风险记录影响、原因和处置建议。

最终输出：
- 需求覆盖情况
- 测试总数、通过、失败和未执行数量
- Bug 发现、根因、修复和回归结果
- 实际执行命令和关键证据
- 残余风险
- 应用是否满足交付条件

没有真实证据时不得宣告通过。
```

# 中断恢复提示词

在任何新会话中输入：

```text
请恢复当前项目的 AIDLC 工作。

不要依赖之前的聊天上下文，直接从项目文件恢复：
1. 检查版本控制状态和现有项目结构。
2. 读取 .aidlc/plan 下全部计划文件。
3. 读取当前阶段相关的 requirements、design、tasks.md 和 src。
4. 根据计划复选框、空白 [Answer]、任务审阅状态和实际产物，判断当前阶段。
5. 保留已有内容和用户改动，从最后一个未完成项继续。

阶段判断顺序：
- 需求计划未完成或需求不完整：需求分析
- 需求完成但设计计划/设计文档不完整：设计
- 设计完成但 tasks.md 未生成或未认可：任务规划
- tasks.md 已认可但有未完成任务：实现
- 任务全部完成但测试未完成：测试与修复

先汇报恢复结果、最后完成项、当前未完成项和准备执行的动作。然后只执行当前阶段的一个最小完整工作段，更新对应文件后停止。
```
